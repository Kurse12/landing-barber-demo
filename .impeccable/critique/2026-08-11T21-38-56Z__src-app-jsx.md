## Overall Impression

The visual craft is intact and holds its own rules honestly — clean detector scan, the poster-fit measurement is real engineering, and the "Vos"/"Turno" fieldset grouping now present in `Booking.jsx` shows the chunking issue flagged in the last critique run has since been fixed. What this run surfaces is sharper and more consequential than last time: this product's entire premise is "disclosure over illusion" — real people should never be able to navigate to a real destination or believe the booking form is real — and that promise has a hole a stress-tester finds in one right-click. Every social link's `href` still points at a real, navigable URL (`instagram.com/barberiaclasica`, `instagram.com/marco.barber`, `maps.google.com/?q=...`); the only thing stopping a visitor from landing there is a `preventDefault()` inside a `click`-only handler, which a middle-click or "open in new tab" skips entirely. That's not a visual defect, it's the product's core safety claim not holding under the exact kind of use a real visitor might casually make.

## What's Working

2. **Booking form's field grouping has been fixed since the last critique run.** `Booking.jsx:198-233` now wraps the seven fields in two `<fieldset>`/`<legend>` groups ("Vos" / "Turno") using the existing mono-label vocabulary — the exact fix the prior run's P3 chunking issue recommended, with correct semantics for screen readers too.
3. **Domain logic is real, not decorative.** `validate()` and `dayScheduleFor()` in `Booking.jsx:36-73` correctly handle the UTC-3 local-date parsing edge case (explained in an inline comment) and block bookings outside actual per-day hours — this is the kind of detail that separates "looks like a booking form" from a form that understands what booking means.

## Priority Issues

**[P0] The demo-disclosure toast is bypassable via middle-click or "open link in new tab," letting real navigation through**
- **Why it matters**: Every disclosure link (`Footer.jsx:127-131` for socials, `Team.jsx:75-79`, `Gallery.jsx`'s Instagram lamina, `Booking.jsx:387-390` for Maps) keeps a real `href` — `https://instagram.com/barberiaclasica`, `https://instagram.com/marco.barber`, `https://maps.google.com/?q=Calle+Principal+123+Buenos+Aires` — and relies on `onClick={(e) => { e.preventDefault(); showDemoToast(...) }}` to stop navigation. A middle-click fires `auxclick`, not `click`, so React's handler never runs; right-click → "open in new tab" fires no click event at all. In both cases the browser follows the real `href` straight through. This directly contradicts PRODUCT.md's explicit constraint that outbound links "must not navigate to a real destination" — and it's the one issue this run found that the mechanical detector structurally cannot catch, since it's a runtime interaction gap, not a static pattern.
- **Fix**: Remove the real destination from `href` (use `href="#"` or drop `href` and use a `<button>` styled as a link with keyboard handling), so there is no real URL to fall through to regardless of click type.
- **Suggested command**: `/impeccable harden`

**[P1] Booking form's demo-disclosure fires only after the user submits, not before**
- **Why it matters**: `Booking.jsx:343-345` is the only "this isn't real" notice in the entire booking flow, and it appears in the success message *after* a visitor has typed their real name and phone and clicked submit, believing "Confirmamos por WhatsApp" (`Booking.jsx:178`). Every other disclosure on the page fires before or at the point of the action it's disclosing; the booking form — the single highest-stakes surface, where personal data changes hands — is the one place it fires last. This is the same issue the last critique run flagged and it is still unresolved.
- **Fix**: Add a short mono note near the submit button or in the section subtitle (e.g. "Formulario de demostración, no se envía a ningún lado") so the disclosure lands before the user commits the effort of filling seven fields.
- **Suggested command**: `/impeccable clarify`

**[P1] `tel:`/`mailto:` links carry zero disclosure, breaking the pattern every other outbound link follows**
- **Why it matters**: Social links, the Maps link, and the legal-page stubs all intercept with `preventDefault()` + toast (`Footer.jsx`, `Team.jsx`, `Booking.jsx`). The `tel:`/`mailto:` links in `Footer.jsx:90-101`, `Booking.jsx:400-411`, and `MobileBar.jsx` have no `onClick` at all — tapping "Llamar" genuinely invokes the phone dialer with `business.phoneHref` (`+541122223333`), a syntactically real, currently-assignable Argentine number. Combined with the P0 bypass, this means every real-looking outbound channel on the page (social, maps, phone) can currently connect to something real, with no consistent rule for which ones are "safe."
- **Fix**: Either intercept `tel:`/`mailto:` with the same toast for consistency, or explicitly decide and document why phone/email are the deliberate exception.
- **Suggested command**: `/impeccable harden`

**[P2] Booking's error-message animation still violates DESIGN.md's own motion rule**
- **Why it matters**: DESIGN.md §7 states as a hard rule: "Solo `transform` y `opacity`. Nunca `width`, `height`, `top`, `left`." `Booking.jsx:100-102`'s `Field` component animates the error message with `height: 0 → 'auto'`, directly contradicting the system's own documented constraint — the exact class of layout-thrash animation that rule exists to prevent. This was flagged in the last critique run and is still present.
- **Fix**: Animate `opacity` against a pre-reserved max-height, or use a transform-based reveal (e.g. `scaleY` from a `transform-origin: top`), instead of animating `height`.
- **Suggested command**: `/impeccable polish`

**[P2] Selecting a service in `Services.jsx` doesn't carry through to the booking form**
- **Why it matters**: `Services.jsx:112-114` scrolls to `#reserva` on click but never passes which service was chosen; `Booking.jsx`'s `<select>` always defaults back to `services[0].id`. A visitor who deliberately picked "Ritual de la casa" from the price list has to re-find and re-select it in a dropdown seconds later — a pure recall tax with no payoff, on a page whose whole design language (mono tabular pricing) is built around not making the user hold data in their head.
- **Fix**: Pass the clicked service's id (URL hash param, or shared bit of state) and pre-select it in Booking's initial form state.
- **Suggested command**: `/impeccable layout`

This is exactly the edge case a methodical stress-tester is built to probe, and it undermines the product's central safety claim in one interaction that requires no special tooling.

**Jordan (First-Timer)**: Types a real name and phone number into the booking form on the strength of "Confirmamos por WhatsApp," with no warning it's fake until after submission — the same gap flagged last run, still open. For a project whose stated principle is "disclosure over illusion," this is the one place a first-time visitor is least protected, and it's the highest-stakes form field on the page.

**Sam (Accessibility-Dependent)**: `Testimonials.jsx` swaps quote, author, and rating content on every arrow click with no `aria-live` region — a screen-reader user navigating the carousel gets no announcement that content changed, unlike Booking's correctly-used `role="status"` for its submit confirmation. Worth a one-line fix (`aria-live="polite"` on the figure) for consistency with the rest of the form's accessibility discipline.

- No hard-ban violations found for emojis, rounded corners, shadows, glass/blur, gradients, or em/en dashes in visible text — the detector's clean scan and manual spot-checks agree here.
- The submit-button label crossfade (`Booking.jsx:321-329`, `filter: blur(3px→0px)`) sits close to DESIGN.md §9's "sin cristal ni desenfoque" ban, though it's a 180ms text-only transition solving a real overlap-during-swap problem, not glassmorphism — still worth a second look given the doc's language is unqualified.
- Desktop nav shows 6 links plus a CTA simultaneously (`Navbar.jsx:89-99`), and Booking's "Turno" fieldset groups 5 fields under one legend — both exceed the ≤4-item chunking guideline, though neither uses an unfamiliar pattern (top nav, form fieldset), so this is a deliberate-tradeoff flag, not a defect.
