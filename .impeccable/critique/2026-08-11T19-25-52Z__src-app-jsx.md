## Overall Impression

This is a well-executed system with real engineering behind its signature moves (measured poster typography, a systemic demo-disclosure pattern), and it holds its own monochrome rules honestly — the clean detector scan backs that up. The gap isn't visual craft, it's that the site's one genuinely risky moment — a stranger typing their real name and phone number into a form that promises "Confirmamos por WhatsApp" — doesn't disclose it's fake until *after* they've submitted it. Everywhere else on the page, the disclosure fires before or at the point of action; here it fires after.

## What's Working

1. **`usePosterFit` (`src/hooks/usePosterFit.js`)** — measures real rendered width per line, waits on `document.fonts.ready`, re-measures on `ResizeObserver`. This is the kind of typographic engineering DESIGN.md's "la medida espera a la fuente" section describes, actually implemented, not just documented.
2. **The demo-disclosure pattern is systemic, not bolted on.** `showDemoToast` fires identically from Footer, Team, Gallery, and Booking's Maps link, intercepting the click before navigation in every one of those cases.
3. **Mobile is a separate design, not a shrunk desktop**, exactly as DESIGN.md §6 mandates: `MobileBar`'s two-block CTA, in-row service photo instead of a cursor preview, native-scroll gallery instead of a hijacked horizontal pin.

## Priority Issues

**[P1] Booking form has no upfront "this is a demo" signal**
- **Why it matters**: A visitor who scrolls straight to `#reserva` (or taps "Sacar turno" in the nav/MobileBar) fills in their real name and phone believing "Confirmamos por WhatsApp" (`Booking.jsx:122`) is a real promise. The disclosure ("Es una demo, así que no se envía a ningún lado de verdad") only appears in the success state *after* submission (`Booking.jsx:259-261`) — every other outbound action on the page discloses before or at the point of click.
- **Fix**: Add a small mono note near the submit button, in the same visual language as field labels, stating the demo status before the user commits the effort of filling seven fields.
- **Suggested command**: `/impeccable clarify`

**[P1] Error-message animation violates DESIGN.md's own motion rule**
- **Why it matters**: DESIGN.md §7 states as a hard rule: "Solo `transform` y `opacity`. Nunca `width`, `height`, `top`, `left`." `Booking.jsx:61-63`'s `Field` component animates the error message with `height: 0 → 'auto'`, directly contradicting the system's own documented constraint (this is exactly the kind of layout-thrash animation the transform/opacity-only rule exists to prevent).
- **Fix**: Animate `opacity` plus a pre-reserved max-height, or use a transform-based reveal, instead of animating `height`.
- **Suggested command**: `/impeccable polish`

**[P2] `tel:`/`mailto:` links silently break the disclosure pattern every other outbound link follows**
- **Why it matters**: Social links (Footer.jsx), Maps (Booking.jsx:299-310), and the legal-page stubs (Footer.jsx:166-171) all `preventDefault()` and show a demo toast. The `tel:`/`mailto:` links in both Footer (`Footer.jsx:87,93`) and Booking (`Booking.jsx:317,323`) don't — they open the visitor's dialer/mail client for real. The underlying number and address are clearly placeholder ("11 2222 3333", "Calle Principal 123"), so there's no real-world harm, but the interaction pattern is inconsistent: nothing on the page signals to a user why some links intercept and others don't.
- **Fix**: Either intercept `tel:`/`mailto:` with the same toast for consistency, or leave them live but say why in a one-line code comment (and consider whether that's actually the intended exception).
- **Suggested command**: `/impeccable harden`

**[P2] No focus trap in mobile nav or lightbox**
- **Why it matters**: `Navbar.jsx` (mobile menu) and `Gallery.jsx` (lightbox) both lock body scroll and close on Escape, but neither traps `Tab` inside the open panel nor returns focus to the trigger element on close. A keyboard/screen-reader user can tab out of an open panel into obscured content behind it.
- **Fix**: Add a focus trap (first/last focusable element wrap-around) and restore focus to the triggering element (hamburger button, gallery thumbnail) on close.
- **Suggested command**: `/impeccable audit`

**[P3] Booking form's 7 fields aren't chunked**
- **Why it matters**: The Cognitive Load checklist fails "chunking ≤4 items/group" here — `Booking.jsx` renders name, phone, service, barber, date, time, and notes in one flat grid with no sub-grouping, despite the system already having a mono-label vocabulary (`label` utility, `SectionHeading`) that could split it into "Vos" / "Turno" groups.
- **Fix**: Add two lightweight mono sub-headers ("Vos" / "Turno") inside the existing grid to group personal-info fields from appointment fields — no new visual language needed.
- **Suggested command**: `/impeccable layout`

Same gap in `Gallery.jsx`'s lightbox.

**Casey (Distracted Mobile)**: The desktop discoverability cue for tappable service rows (`hover:bg-chalk` row-invert in `Services.jsx`) never fires on touch — there's no equivalent tap affordance, so a service row can read as static text rather than a link toward booking.
